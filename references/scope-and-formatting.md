# 范围判定、上下文工程规范与格式化参考

## 1. 全局 vs 项目 vs Skill 作用域判定

遵循**作用域最小化**原则，信息按以下三层存放：

| 层级 | 适用内容 | 典型例子 |
| :--- | :--- | :--- |
| **全局规则** | 跨项目通用且高频生效的偏好与安全红线 | 默认中文、先说结论、Node 默认 `pnpm`、不擅自 Git 写操作/启后台服务、不把私有代码发给外部搜索 |
| **项目规则** | 仅当前仓库适用的技术栈、结构与业务约定 | 本项目用 Vue 3 + Element Plus、路由放 `src/routes/`、特定测试脚本 |
| **Skill（按需加载）** | 长流程、专项操作指南、阶段性规范 | 发布流水线、数据库调试、规则审计与调优流程 |

## 2. 上下文工程（Context Engineering）防膨胀准则

1. **信号隔离（Ephemeral vs Persistent）**：
   - 单次任务例外（“这次把完整代码发我”）→ 不入库。
   - 偶发报错 → 当次修复，不立刻写全局规则。
   - 跨会话重复 ≥ 2~3 次，或用户明确长期要求 → 提炼入库。
2. **注意力预算（Attention Budget）**：
   - 全局规则建议保持在 **30 行（约 15 条）以内**。
   - 禁止写入现代编码代理已自带的约束（如“Plan Mode 不改文件”“改完运行相关测试”“不虚报结果”“不覆盖未提交修改”）。
3. **一进一出与合并优先**：
   - 新规则能并入已有条款的，直接改写原句，不另起一行。
   - 接近预算上限时，必须先删掉过时/已由模型原生覆盖的规则，或将长内容拆入 Skill。
4. **可执行、反模糊**：
   - 避免“写高质量代码”“注意性能”，改为“几十行内可用标准库解决时不新增依赖”。

## 3. 写入前检查清单

- [ ] 是否属于跨会话长期偏好（非单次临时指令）？
- [ ] 是否放在了最小合适的作用域（Skill > 项目 > 全局）？
- [ ] 是否与模型内置能力重复？
- [ ] 是否已查重并优先合并到现有条款？
- [ ] 全局总行数是否仍在预算范围内（建议 ≤ 30 行）？
- [ ] 修改前是否已备份（Magpie 自动备份或 `.bak`）？
